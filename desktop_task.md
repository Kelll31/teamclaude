# TASK: TeamClaude / TeamRouter Desktop — Cross-platform Desktop Application

**Repository:** https://github.com/KarpelesLab/teamclaude

**Task type:** Major Feature / Desktop Application

**Target platforms:** Windows 10/11 x64, Linux x64

**Suggested stack:** Electron + React + TypeScript + Vite

**Priority:** High

**Goal:** Разработать полноценное десктопное приложение для управления TeamClaude/TeamRouter с поддержкой Windows и Linux, не нарушая обратную совместимость с оригинальным CLI.

---

## 1. Общая цель

Необходимо превратить существующий TeamClaude в удобное desktop-first приложение, которым можно полноценно пользоваться без постоянной работы с терминалом.

Приложение должно предоставлять графический интерфейс для:

- Управления несколькими аккаунтами Claude, Codex и поддерживаемых API-провайдеров.
- Просмотра квот, лимитов и времени их сброса.
- Автоматической ротации аккаунтов.
- Управления прокси-сервером.
- Отслеживания активных сессий и запросов.
- Настройки правил распределения нагрузки.
- Просмотра логов и диагностики ошибок.
- Управления фоновым режимом.
- Подключения официальных CLI-клиентов и VS Code.

**Ключевой принцип:** приложение должно использовать существующий TeamClaude как backend, а не реализовывать заново его систему маршрутизации, OAuth и квот.

Desktop GUI является дополнительным способом управления локальным прокси, а не новым клиентом для расходования подписочных квот.

Приложение предназначено для одного владельца собственных аккаунтов в рамках существующей модели безопасности проекта.

## 2. Анализ существующего проекта

Перед написанием кода необходимо:

1. Изучить актуальную структуру репозитория.
2. Прочитать `README.md`, `CONTRIBUTING.md`, `SECURITY.md`.
3. Изучить `docs/usage.md`, `docs/accounts.md`, `docs/configuration.md`, `docs/compliance.md`.
4. Найти существующие API управления сервером и аккаунтами.
5. Определить, какие функции доступны через HTTP API, какие только через CLI, а какие требуют доступа к внутреннему состоянию.
6. Изучить реализацию встроенного браузерного dashboard.
7. Определить безопасный способ запуска Node.js backend внутри упакованного приложения.
8. Проверить существующие решения для управления фоновым процессом.
9. Проверить текущую миграцию названия TeamClaude → TeamRouter.

Не дублировать существующие возможности и не изменять внутреннюю архитектуру без необходимости.

Подготовить краткий архитектурный документ `docs/desktop-architecture.md`.

## 3. Технологический стек

Предлагаемая архитектура:

| Компонент | Технология |
|---|---|
| Desktop runtime | Electron |
| Frontend | React + TypeScript |
| Build | Vite |
| UI | Tailwind CSS |
| Компоненты | shadcn/ui или эквивалент |
| Иконки | Lucide |
| Графики | Recharts |
| Backend | Существующий TeamClaude |
| IPC | Electron preload + typed IPC |
| Packaging | electron-builder |
| Tests | Vitest + Playwright / Electron testing |
| CI/CD | GitHub Actions |

Допускается выбор другой технологии при наличии обоснованных преимуществ.

Требования:

- Никаких новых runtime-зависимостей в ядре TeamClaude.
- Зависимости Desktop UI изолированы в собственном пакете.
- CLI продолжает работать без установленного Desktop.
- Desktop не требует глобальной установки CLI, Node.js или npm у конечного пользователя.
- Строгая типизация TypeScript в новом коде.
- Отсутствие циклических зависимостей между GUI и backend.

Предлагаемая структура:

- `desktop/` — отдельный пакет десктопного приложения.
- `desktop/src/main/` — Electron main process.
- `desktop/src/preload/` — безопасный IPC-мост.
- `desktop/src/renderer/` — React-интерфейс.
- `desktop/src/services/` — управление backend и системная интеграция.
- `desktop/src/components/` — повторно используемые UI-компоненты.
- `desktop/src/pages/` — страницы приложения.
- `desktop/resources/` — иконки и ресурсы приложения.
- `desktop/tests/` — тесты.
- `desktop/electron-builder.yml` — конфигурация упаковки.
- `docs/desktop.md` — документация.

Структуру уточнить после исследования проекта.

# 4. Основные функциональные модули

## 4.1. Dashboard / Overview

Создать главную страницу с отображением состояния всего пула аккаунтов.

**Элементы интерфейса:**

- Состояние прокси: Running / Stopped / Starting / Error.
- Версия TeamClaude и Desktop.
- Адрес локального прокси.
- Количество зарегистрированных аккаунтов.
- Количество доступных аккаунтов.
- Количество исчерпавших квоту аккаунтов.
- Активный аккаунт для каждого провайдера.
- Количество текущих сессий.
- Количество обработанных запросов.
- Текущие ошибки и предупреждения.

**Визуализация:**

- Карточки основных метрик.
- Прогресс-бары оставшихся квот.
- Время до обновления 5-часового лимита.
- Время до обновления недельного лимита.
- График активности при наличии доступной статистики.
- Индикатор свежести данных.

Не рассчитывать оставшуюся квоту по выдуманным значениям. Использовать только данные, реально полученные от backend.

При недоступности данных показывать Unknown / Not available.

## 4.2. Account Manager

Создать отдельную страницу управления аккаунтами.

**Функциональность:**

- Просмотр всех аккаунтов.
- Группировка по провайдеру.
- Добавление Claude-аккаунта через существующий OAuth-механизм.
- Импорт существующего аккаунта, если backend поддерживает операцию.
- Добавление поддерживаемых API-key провайдеров.
- Удаление аккаунта с подтверждением.
- Временное отключение и повторное включение.
- Изменение приоритета.
- Ручной выбор предпочтительного аккаунта.
- Обновление информации.
- Отображение ошибок авторизации.
- Повторная авторизация при истечении токена.

Каждая карточка аккаунта должна показывать:

- Название.
- Email или отображаемый идентификатор.
- Провайдера.
- Тип подписки, если доступен.
- Статус токена без отображения его значения.
- Статус доступности.
- Использование квоты.
- Время следующего сброса.
- Приоритет.
- Участвует ли аккаунт в ротации.

**Авторизация:**

Использовать уже существующий OAuth-flow TeamClaude. Не реализовывать собственную OAuth-систему.

Открывать системный браузер, принимать результат через существующий механизм callback или безопасный адаптер.

Если существующий CLI поддерживает только интерактивный вход, для MVP допускается запуск поддерживаемого терминального процесса. Полноценный GUI OAuth-flow реализовать отдельным этапом через переиспользование существующих модулей.

Нельзя получать токены из логов, парсить их из отображаемого текста или передавать в renderer.

## 4.3. Proxy Server Manager

Реализовать управление жизненным циклом прокси.

**Действия:**

- Start Server.
- Stop Server.
- Restart Server.
- Refresh Status.
- Open Web Dashboard.
- View Logs.
- Copy Local Endpoint.

Backend должен работать без открытого терминала в headless-режиме.

**Сценарии:**

1. Desktop запускается, сервер остановлен — доступна кнопка Start.
2. Desktop запускается, сервер уже работает — приложение подключается к существующему экземпляру.
3. Сервер завершился с ошибкой — отображаются диагностика и действия восстановления.
4. Сервер перестал отвечать — состояние Offline / Unreachable.
5. Пользователь закрывает окно — сервер продолжает работать, если включён режим сворачивания в трей.
6. Пользователь выбирает Quit — приложение корректно завершает только те процессы, которыми владеет, согласно выбранным настройкам.

Важно:

- Не допускать случайного запуска двух backend-процессов на одном порту.
- Не завершать сторонние процессы при конфликте порта.
- Отличать сервер, созданный Desktop, от уже запущенного внешнего сервера.
- Проверять готовность сервера фактическим запросом, а не фиксированным таймером.
- Реализовать корректное завершение дочернего процесса на Windows и Linux.
- Исключить бесконечный цикл перезапусков при систематическом падении.
- Сохранять возможность запуска оригинального CLI независимо от GUI.

## 4.4. Rotation & Routing Settings

Создать страницу визуальной настройки ротации.

**Управление:**

- Включение и отключение распределения новых сессий.
- Настройка switch threshold.
- Управление приоритетами аккаунтов.
- Ручное переключение аккаунта.
- Настройка поддерживаемых модельных маршрутов.
- Просмотр причин недоступности аккаунта.
- Управление существующими настройками probe и warmup.

Отображать выбранный режим распределения, текущий активный аккаунт и ограничения по моделям.

Не путать пер-минутный rate limit с исчерпанием квоты.

Не переписывать алгоритмы ротации TeamClaude.

Использовать существующие команды и control API.

Настройки, способные расходовать дополнительные запросы или платный лимит, должны быть выключены по умолчанию и сопровождаться предупреждением.

## 4.5. Sessions & Activity Monitor

**Функциональность:**

- Идентификатор или название сессии.
- Используемая модель.

- Фильтрация по аккаунту, провайдеру и модели.
- Отображение событий переключения.
- Фильтрация ошибок.

Добавить журнал маршрутизации запросов без чувствительных данных.

Если существующий API предоставляет только агрегированную статистику, не изобретать несуществующие сведения о сессиях. Дополнительную серверную телеметрию рассматривать как отдельное расширение, согласуемое с мейнтейнерами.

# 6. Архитектура Desktop

## 6.1. Main Process

Main Process отвечает за:

- Создание окна.
- Управление системным треем.
- Запуск и завершение backend.
- Доступ к разрешённым локальным системным функциям.
- Безопасные IPC-обработчики.
- Системные уведомления.
- Автозапуск.
- Управление жизненным циклом приложения.

## 6.2. Renderer Process

Renderer содержит только интерфейс.

Он не должен:

- Читать файлы с OAuth-токенами.
- Иметь прямой доступ к Node.js API.
- Выполнять произвольные shell-команды.
- Получать доступ ко всему файловому окружению.
- Самостоятельно управлять дочерними процессами.

Все привилегированные действия выполняются через строго ограниченный preload API.

## 6.3. Backend Adapter

Реализовать отдельный адаптер взаимодействия с TeamClaude.

Он должен:

- Получать состояние сервера.
- Выполнять разрешённые управляющие операции.
- Обрабатывать ошибки API.
- Поддерживать отмену и таймауты.
- Проверять версию и совместимость backend.
- Учитывать префиксы TeamClaude и TeamRouter.
- Нормализовать данные для UI.

Использовать типизированные модели и проверку входящих данных.

Не привязывать React-компоненты напрямую к внутренней структуре backend.

## 6.4. Bundled Backend Runtime

Десктопная сборка должна запускаться на чистой системе без установленного Node.js.

Необходимо выбрать и реализовать безопасный вариант:

- Запуск Node backend через Electron runtime в отдельном процессе, если это совместимо с упаковкой.
- Либо включение отдельного поддерживаемого Node.js runtime в пакет приложения.

Проверить оба режима на Windows и Linux, учитывая содержимое ASAR, доступ к файлам и особенности запуска subprocess.

Не использовать глобальные зависимости или непредсказуемый PATH конечного пользователя для обязательных компонентов.

# 7. Безопасность

Безопасность является обязательным критерием приёмки.

**Electron:**

- `contextIsolation: true`.
- `nodeIntegration: false`.
- `sandbox: true` там, где применимо.
- Минимальный preload API.
- Строгая валидация IPC.
- Запрет произвольной навигации.
- Запрет исполнения удалённого кода.
- Content Security Policy.
- Никакого произвольного `shell.execute`.
- Запуск внешних ссылок через безопасный системный обработчик.

**Backend:**

- По умолчанию слушает только loopback-интерфейс.
- Не делает управляющие маршруты доступными внешней сети без явной настройки.
- Не отключает существующие проверки Origin и авторизации.
- Не хранит чувствительные данные в renderer или localStorage.
- Не выводит секреты в логи.
- Не отправляет телеметрию без согласия.
- Не изменяет правила доступа к подпискам.
- Не запускает shell с интерполированными пользовательскими аргументами.
- Не требует административных прав без явной необходимости.

Все аккаунты принадлежат одному оператору. Не добавлять функции совместного использования аккаунтов, реселлинга, мультиарендности или обхода модели доступа провайдеров.

Отдельно изучить требования `SECURITY.md` к подлинности дистрибутивов. До согласования с мейнтейнерами не выдавать сторонние установочные файлы за официальные релизы проекта.

# 8. Windows Support

Целевая платформа: Windows 10/11 x64.

**Требования:**

- Полноценная поддержка PowerShell и Windows Terminal.
- Запуск приложения без командной строки.
- Корректная обработка путей с пробелами и Unicode.
- Работа под обычной пользовательской учётной записью.
- Корректная работа OAuth в системном браузере.
- Устойчивый запуск и остановка фоновых процессов.
- Отсутствие зависших дочерних процессов после завершения.
- Сохранение существующих аккаунтов при переустановке.
- Проверка конфликтов локальных портов.
- Обработка блокировки порта или процесса антивирусом.

**Особый регрессионный сценарий:**

Проверить поведение на Windows при завершении CLI-команд и backend с ошибкой Node/libuv:

`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 94`

Не скрывать падение в интерфейсе. Определить, воспроизводится ли оно с выбранным runtime, и обеспечить корректную диагностику.

**Артефакты сборки:**

- Windows `.exe` installer.
- Опциональная portable-сборка.
- Понятные инструкции установки.
- Корректное удаление приложения без автоматического удаления пользовательских аккаунтов и конфигурации.

# 17. Instructions for Coding Agent

Ты работаешь непосредственно с существующим репозиторием TeamClaude.

**Не создавай демонстрационную оболочку с фейковыми данными вместо работающего приложения.**

Последовательность работы:

1. Изучи репозиторий, существующие модули и ограничения CONTRIBUTING.
2. Составь архитектурный план и карту переиспользуемых API.
3. Укажи потенциально несовместимые изменения и отдели их от Desktop-only кода.
4. Реализуй минимальный вертикальный сценарий: запустить Desktop → стартовать backend → получить реальный статус → вывести данные.
5. Постепенно добавляй модули по фазам.
6. После каждого этапа выполняй соответствующие тесты и сборку.
7. Не игнорируй ошибки TypeScript и ESLint.
8. Не создавай скрытые обходные решения, дублирующие backend.
9. Не добавляй новые серверные API без реальной необходимости.
10. Не ломай существующий npm-пакет.
11. Все изменения сопровождай документацией.
12. Фиксируй подтверждённые результаты тестирования отдельно от непроверенных предположений.

В конце предоставь:

- Список реализованных функций.
- Список изменённых и добавленных файлов.
- Команды запуска в development mode.
- Команды сборки Windows/Linux.
- Результаты тестов.
- Известные ограничения.
- Инструкции по установке.
- Предлагаемое разделение изменений на Pull Requests.

**Главная цель: создать настоящий, удобный, безопасный TeamClaude Desktop, который можно развивать вместе с оригинальным open-source проектом.**
